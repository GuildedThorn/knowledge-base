## Purpose

Compute-saving techniques for game/bot AI (pathfinding, decision-making, per-tick updates) applicable to a dedicated server ticking many simultaneous agents. Compiled 2026-07-24 for direct application to [SkyDestroyer - Overview](kb://07-projects-skydestroyer-skydestroyer-overview), whose bot AI (`NavGraph.cs`, `BotObject.cs`, `MasterAI.cs`, `CtfMasterAI.cs`, `CnhMasterAI.cs`, `BotManager.cs`, `PathKeeper.cs`) is ported byte-faithfully from the original C++ and ticks every game-mode bot every server frame. Complements [Game CPU Performance and Profiling](kb://06-reference-game-cpu-performance-and-profiling) (general CPU/GC discipline) — this note is specific to AI decision/pathing cost.

**Porting-ledger caveat**: SkyDestroyer's stated policy is byte-faithful port fidelity, verified live-rig before anything is marked done ([SkyDestroyer - Overview](kb://07-projects-skydestroyer-skydestroyer-overview)). None of the techniques below should be applied *inside* the ported fidelity-tracked bot AI files without checking `docs/PORTING.md` first — changing `MasterAI.cs`/`NavGraph.cs` behavior risks diverging from the original and breaking rig-tested parity. The techniques marked "safe to add" below sit *around* the ported code (caching, scheduling, spatial indexing) rather than changing its logic, so they preserve behavioral fidelity while cutting CPU cost.

## Time-Slicing / Update Throttling (safe to add — highest ROI, lowest risk)

Not every bot needs full AI re-evaluation every tick. Split the bot population across N buckets (e.g. by `bot.Id % N`) and only run expensive decision logic (target selection, path replan) for one bucket per tick, round-robin — cheap state (movement interpolation, aim tracking) still updates every tick, only the costly reasoning is staggered. This is the single cheapest lever for a server ticking many bots, because most game AI decisions (who to attack, where to go next) don't actually need to be recomputed at the full server tick rate — the original game already ran this with a fixed tick, so bucketing changes *when* MasterAI reasons, not *what* it decides, keeping port fidelity if implemented as a wrapper around the existing per-bot brain call rather than inside it.

- **AI LOD by relevance, not just distance**: since this is a server (no player camera to measure "distance" against), the analogous relevance signal is *is any human player near this bot / can any player perceive its outcome soon* (e.g. same base/zone, in combat, carrying the flag). Bots far from any live contest can drop to a coarser tick rate (e.g. 1-in-4 ticks) without a player ever noticing; bots in an active firefight or holding the flag should stay full-rate.
- Pair with a "catch-up" step for anything suspended longer than one tick (accumulated movement/damage-over-time) so throttled bots don't visibly desync when they resume — same pattern as Conan Exiles' AI LOD suspend/resume model.

## Pathfinding Cost Reduction

- **Cache/reuse path results (safe to add)**: if multiple bots on the same team/objective need to reach the same destination (same flag, same capture point), compute one path/flow field to that destination and let all bots heading there share it, instead of each bot running its own independent search. This doesn't change any single bot's chosen path if the search is deterministic — it just avoids redundant identical searches, which is a pure win for a CTF/CnH game mode where objectives concentrate a lot of bots on the same targets.
- **Flow fields for many-agent shared destinations**: when many agents move toward one goal (a team assaulting a flag), a single flow-field build (Dijkstra/BFS flood from the goal, O(N) to O(N log N) once) lets every agent read a direction in O(1), instead of each agent paying its own A* search — the technique that let Supreme Commander 2 and Planetary Annihilation move thousands of units cheaply. Most relevant to CTF/CnH where destinations cluster; less relevant to Hunter, where targets are more individualized.
- **Hierarchical pathfinding (HPA*)** is the right lever if per-bot searches on the full nav-graph are themselves the bottleneck (long-range paths across a big map): precompute cluster-to-cluster costs once, search coarse-to-fine. Reported up to ~10x faster than a well-optimized flat A*, at ~1% path-length cost versus optimal. Higher implementation risk here than the other items since it changes the nav-graph structure `NavGraph.cs` builds on — evaluate against the porting-ledger policy before touching, since the original AADS bot pathing is presumably flat-graph and any HPA* layer would need to reproduce equivalent paths to stay rig-parity-safe, or be scoped as an explicitly-new (not ported) optimization.
- **Spatial partitioning for nav/target queries (safe to add)**: a uniform grid outperforms quadtrees/k-d trees for "who/what is near me" queries at typical agent-per-cell densities (research comparison found regular grid fastest, quadtree slowest) — use a grid (not a tree) for `BotManager`'s nearest-enemy/nearest-pickup/nearest-flag-carrier lookups if those are currently linear scans over all entities, which is the likely cost for something like the sensor/target-selection phase of `MasterAI`.

## Decision-Layer Cost (informational — original AI is fixed architecture, don't rewrite)

SkyDestroyer's bot brains (`MasterAI`/`CtfMasterAI`/`CnhMasterAI`) are already ported from the original C++ decision logic and shouldn't be re-architected for fidelity's sake, but this is useful context for evaluating *why* a decision step might be showing up hot in a profile, and for any genuinely new (non-ported) bot behavior added later:

- **Utility AI vs GOAP vs Behavior Trees, CPU-wise**: reported findings show GOAP's per-frame target/plan recalculation can cost multiple ms/frame (one write-up measured ~4ms for target recalculation alone), where a utility-scoring approach doing the equivalent per-target scoring is comparatively trivial. Behavior trees sit in between — cheaper than replanning, more rigid than utility scoring. If a *new* AI system is ever added outside the ported bot brains, utility scoring is the cheaper default versus a GOAP-style planner.
- **Influence maps** are a cheap layer for spatial/tactical awareness (threat/occupancy/proximity summed over a grid) that complements rather than replaces pathfinding — relevant if a future non-ported feature needs "where is it currently dangerous" reasoning without a full line-of-sight sweep per bot per tick, since the expensive analysis (LOS, threat sourcing) is precomputed once into the map and every bot just reads a cell value.

## Parallelizing Bot Ticks (C#/.NET, dedicated server)

- Splitting one thread per subsystem (pathfinding thread, sensor/perception thread, decision thread) is the classic AI-multithreading split, but the real difficulty is synchronization: agents reading world state written by other agents mid-tick. The two-stage pattern — a **collection stage** where each bot computes its intended change against a read-only snapshot of world state, followed by an **apply stage** that commits all changes serially — avoids race conditions without locking every access, and maps cleanly onto a tick-based server loop (`PacketShipLoop`/`LifecycleLoop` in `SkyDestroyer.cs` already has a natural tick boundary to slot an apply stage into).
- In .NET terms: `Parallel.ForEach` (or manually partitioned `Task.Run` batches) over the bot list for the read-only "decide" stage, since each bot's decision can be computed independently against the previous tick's snapshot; the "apply" stage (writing positions, firing weapons, damaging players) stays single-threaded to avoid touching shared mutable state (connection manager, player list) from multiple threads at once.
- Server GC (as opposed to Godot's client-default Workstation GC — see [Game CPU Performance and Profiling](kb://06-reference-game-cpu-performance-and-profiling)) is a clearer win here since SkyDestroyer *is* the dedicated server case that note flags as worth testing — per-core heaps suit a multi-threaded bot-decide stage better than a single client-side render thread.
- This is additive infrastructure (a scheduler around the existing per-bot decide/apply calls), not a change to bot logic, so it's lower fidelity-risk than touching pathfinding/decision internals — the main engineering cost is proving the collect/apply split doesn't change bot behavior versus the current sequential tick, which the existing `Tests/SkyDestroyer.Tests.csproj` round-trip suite is well-positioned to verify.

## Practical Priority Order for SkyDestroyer

1. Profile first (per [Game CPU Performance and Profiling](kb://06-reference-game-cpu-performance-and-profiling)) — confirm bot AI is actually the hot path per-tick before optimizing it; with full gameplay simulation already live and rig-tested, the bottleneck may be elsewhere (physics, networking serialization).
2. If bot AI is hot: bucketed time-slicing of the decide step first — cheapest, lowest fidelity risk, no logic change.
3. Grid-based spatial queries for nearest-entity lookups in `BotManager`/`MasterAI` sensor logic — likely the second-cheapest win if those are linear scans.
4. Shared path/flow-field caching for CTF/CnH objective rushes — meaningful if profiling shows redundant identical pathfinding calls across bots heading to the same flag/point.
5. Collect/apply parallel tick — bigger engineering lift, save for if single-threaded bot-decide cost is still the ceiling after 2-4.
6. HPA* or any nav-graph structural change — last resort, highest fidelity risk, only if per-bot path search cost on the existing flat graph is proven (via profiler) to dominate.
