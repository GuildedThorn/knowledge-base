## Purpose

Survey of techniques for cutting LLM compute/token cost — model-level, serving-level, and application-level — plus what's directly applicable to how this vault's AI-driven systems ([vr-brain - Overview](kb://07-projects-vr-brain-vr-brain-overview), [ThornBot - Overview](kb://07-projects-thornbot-thornbot-overview)) and day-to-day Claude Code usage spend tokens. Compiled 2026-07-24, deepened same day with agentic-context-management specifics, RAG-vs-long-context numbers, PEFT fine-tuning, and known failure modes. Complements [Local Embedding Models for Semantic Search](kb://06-reference-local-embedding-models-for-semantic-search) (running embeddings locally rather than via API).

## Model-Level (only relevant if self-hosting/fine-tuning — not applicable to hosted Claude use)

- **Quantization**: reducing weight precision (FP16 → INT8/INT4/FP8) cuts memory 2-4x and inference cost roughly in half, typically retaining 95-99% of original accuracy; FP8 is the most stable low-precision format on modern accelerators with native support. Only relevant to self-hosted models — hosted Claude usage doesn't expose this lever.
- **Knowledge distillation**: train a smaller model to mimic a larger one's outputs rather than training from scratch — the mechanism behind Anthropic's own Haiku-tier models being cheap-but-capable relative to Opus-tier.
- **Pruning**: remove redundant weights/attention heads post-training; a lower-effort, lower-payoff sibling of distillation.
- **Mixture-of-Experts (MoE) / sparse activation**: only a subset of the model's parameters (top-k experts, chosen by a router) activate per token, giving trillion-parameter-class capability at a fraction of the compute of an equivalently-sized dense model — reported up to ~70% lower compute versus a dense model of similar total size. This is an architecture choice made by the model provider, not something you configure as a caller — relevant context for *why* newer large models can be both bigger and cheaper per-token than older dense ones.
- **Adaptive/dynamic-depth compute** (early exit, Mixture-of-Depths, Mixture-of-Recursions): instead of every token passing through every transformer layer, a per-layer router lets "easy" tokens skip layers (or exit early) while "hard" tokens get full depth — finer-grained than MoE's per-token expert selection, since it varies *how much* compute a token gets rather than *which* fixed-size expert handles it. Still mostly research/newer-architecture territory (2024-2026 papers) rather than something a caller controls, but explains another axis of "why do some model generations get cheaper/faster without visibly getting weaker."
- **Parameter-efficient fine-tuning (LoRA/QLoRA/adapters)**: only relevant if actually fine-tuning a model (not applicable to calling hosted Claude, which doesn't expose base-weight fine-tuning). Trains ~0.1-1% of parameters instead of the full model — reported ~10-20x memory reduction and roughly 90-95% of full-fine-tune task quality for many tasks, at 50-70% lower training cost. Concretely: full fine-tuning a 7B model needs ~100-120GB VRAM (frontier-GPU-cluster territory); QLoRA fine-tunes the same model on a single consumer-class GPU. Only worth reaching for "full fine-tune" territory when the goal is a substantial behavioral change to the base model itself, not task adaptation.

## Serving-Level (what API providers do — informational, not directly controllable by a caller)

- **PagedAttention / paged KV cache**: manages the attention key-value cache like OS virtual memory — fixed-size non-contiguous pages mapped via a page table — pushing effective GPU memory utilization from ~50-65% to 95%+ under bursty traffic, at ~2-5% compute overhead. This is what lets a provider serve many concurrent long-context requests without the KV cache itself becoming the bottleneck.
- **Continuous batching**: instead of batching fixed groups of requests and padding short ones to the longest, the server continuously admits/retires individual requests into a shared in-flight batch — avoids wasted compute on padding, a major throughput lever (reported up to ~23x versus naive static batching in some benchmarks).
- **Speculative decoding**: a small fast "draft" model proposes several tokens ahead, the large model verifies them in one pass and accepts/rejects — 2-3x latency reduction at no quality loss, because verifying a token is cheaper than generating it autoregressively. Purely a serving-side latency/throughput optimization; doesn't change what you pay per output token but explains why some "fast mode" offerings exist. Its payoff is entirely dependent on the draft model's acceptance rate against the real model's distribution — a mismatched draft model (too different from the target) yields little to no speedup.
- **Prefix/KV-cache sharing across requests** (e.g. SGLang-style prefix reuse): when many concurrent requests share an identical prefix (same system prompt/tool schema), the server reuses that portion of the KV cache instead of recomputing it per request — the serving-side analog of prompt caching, described next.

## Application-Level (the levers you actually control as a caller)

### Prompt caching (Anthropic) — biggest lever for repeated context

Cache reads cost **0.1x** base input price (90% discount); cache writes cost 1.25x base (5-minute TTL) or 2x base (1-hour TTL, worth it when requests are >5 min apart). Minimum cacheable prefix length varies by model (roughly 1024 tokens for current Sonnet/Opus tiers, more for older/smaller tiers) — below that, caching silently no-ops rather than erroring.

- **Ordering matters**: structure requests as `tools → system → messages`, with static content first and a `cache_control` breakpoint placed on the *last block that stays identical across requests* — never on a block containing a timestamp or per-request variable, since that invalidates the whole prefix.
- Up to 4 explicit breakpoints per request — use separate breakpoints for content that changes at different frequencies (tool definitions rarely change; a "today's context" block changes daily; message history changes every turn).
- The cache lookback window is ~20 blocks — a long-running conversation that grows past that between breakpoint updates will miss even though earlier content is technically still cached; add an intermediate breakpoint to avoid this in very long sessions.
- For latency-sensitive services, pre-warm the cache (a zero-output request) before real traffic arrives.
- Track `cache_read_input_tokens` / `cache_creation_input_tokens` / `input_tokens` in the response `usage` block to verify caching is actually landing rather than assuming it.

### Context editing and the memory tool (Anthropic) — the direct answer to "keep long agentic sessions cheap"

Server-side context management purpose-built for exactly this session's shape (a long tool-heavy agentic conversation):

- **`clear_tool_uses_20250919`**: once input tokens cross a trigger threshold (default 100k), automatically clears the *oldest* tool results (file reads, search results) beyond a configurable `keep` count, replacing them with a placeholder so the model still knows something was there. `exclude_tools` protects results you never want auto-cleared (e.g. web search citations you'll reference later).
- **`clear_thinking_20251015`**: prunes old extended-thinking blocks, keeping either the last N turns or all of them. Keeping all thinking preserves prompt-cache hits (no invalidation); clearing thinking saves context space but invalidates the cache for that prefix — a direct tradeoff between "smaller context now" and "cheaper next turn via cache."
- **Interaction with prompt caching is the key gotcha**: clearing tool results *invalidates* the cached prefix from that point forward, so it's only worth doing when `clear_at_least` removes enough tokens to justify eating a fresh cache-write cost. Clearing too aggressively/too often can make a session more expensive, not less, by repeatedly paying 1.25x-2x cache-write rates instead of 0.1x cache-read rates.
- **Memory tool combo**: Claude gets a warning before clearing happens and can write essential facts to a memory file first, then retrieve them later on demand — this is the same shape as this vault's own `MEMORY.md` + per-topic-file pattern, just running at the agent-runtime layer instead of the vault layer. The design principle is identical: keep an index cheap to re-read, push detail into pointer-addressable files instead of inlining everything into the live context.
- **Practical read for this environment**: this session's own automatic context-window compression (mentioned in the system reminder as summarizing older turns) is functionally the client-side/managed equivalent of what `clear_tool_uses`/compaction do server-side for the raw API — the same principle already operating one layer up.

### Batch API — for non-interactive/offline work

50% off both input and output tokens for asynchronous jobs (processed within a time window rather than real-time) — stacks with prompt caching for compounding savings. Fits anything that doesn't need an immediate reply: bulk classification, offline note/summary generation, scheduled digest jobs — a natural fit for something like a scheduled [SOC → vr-brain integration](kb://soc-vrbrain-integration.md) digest or batch-processing archived notes, as opposed to this live voice-driven session which is inherently interactive and can't use it.

### Model routing / cascading — match model tier to task difficulty

Two related strategies: **routing** sends each query directly to the model tier it needs (classify difficulty first, dispatch once); **cascading** tries the cheap model first and escalates only if its output fails a confidence/quality check. Reported cost reductions of 40-85% versus always using the top-tier model, with quality staying near-identical because most real queries don't need the largest model's full capability. Practical shape: a cheap/fast tier for classification, extraction, or routing decisions themselves; escalate to a frontier tier only for the reasoning-heavy remainder. This is the same principle behind choosing `haiku` for a cheap subagent step versus `opus`/`sonnet` for the step that actually needs deep reasoning — see effort/model override options on the Agent and Workflow tools.

### Context compression / compaction

Strip redundant or superseded tokens from conversation history before it's resent — verbatim deletion of noise while preserving surviving content character-for-character (as opposed to lossy summarization, which risks dropping load-bearing detail). This is exactly what this session's own automatic context-window compression does when a conversation grows long, and is the unmanaged/client-side counterpart to Anthropic's server-side context-editing tools above.

### Retrieval (RAG) vs. long-context stuffing

For anything beyond roughly 100K tokens of source material, retrieving only the relevant chunks (RAG, top-20 to top-30 by relevance) is reported to *both* cost over an order of magnitude less **and** perform better on grounded-document tasks than stuffing the full corpus into context — one comparison found long-context prompting averaging ~$0.118/query versus ~$0.0045-0.0046/query for keyword/semantic RAG at equivalent workloads (RAG end-to-end latency ~1s vs. 30-60s for full long-context on the same task), because transformer attention cost scales roughly quadratically with context length, so doubling context roughly quadruples compute. The exception: if the dataset already fits comfortably inside the window and the task genuinely needs global/cross-document reasoning (not "find this one fact"), the retrieval step is pure overhead and long-context wins on accuracy. Rule of thumb: RAG for lookup-shaped questions over a large corpus, long-context/full-document-in-prompt for reasoning that must consider everything at once.

### Semantic caching

Distinct from prompt/prefix caching: instead of matching identical token prefixes, embed the *incoming query* and check it against a cache of previously-answered semantically-similar queries, skipping the LLM call entirely on a hit. Reported ~31% of real-world LLM queries are semantically similar to a prior one, and semantic caching can cut costs up to ~90% on workloads with that kind of repetition (FAQ-style or narrow-domain assistants benefit most; a wide-ranging agentic coding session benefits least, since few requests are truly repeats of an earlier one). **Failure modes worth knowing before adopting it** (see Pitfalls below) — this is the one technique in this note with a real correctness risk, not just a cost/latency tradeoff.

### Structured output / constrained decoding

Forcing output into a schema (JSON schema, grammar) via token-masking at generation time both improves reliability and reduces wasted output tokens (no filler prose around the answer) — modern constrained-decoding engines (e.g. XGrammar-style token-mask caching) make this near-zero-overhead rather than the multi-second-per-token cost naive grammar-constrained decoding used to carry. This is the mechanism behind this environment's own tool-call/schema-forced outputs (e.g. Workflow's `schema` option on `agent()` calls) — using a schema is itself a token-cost optimization, not just a correctness one.

## Pitfalls and Failure Modes (know before adopting)

- **Semantic caching false positives**: a query crossing the similarity threshold but needing a genuinely different answer returns a wrong answer with full confidence (a 200-OK-shaped failure, not an error) — production write-ups note once false-positive rate exceeds ~3-5%, the embedding model itself has hit its ceiling and tightening the threshold further just trades false positives for near-total miss rates instead of fixing anything.
- **Semantic cache staleness**: cached answers are model-generated, not deterministic lookups — they can go stale as underlying facts change with no natural expiry signal unless you explicitly add TTLs or version-tag the cache keys to invalidate on known data changes.
- **Embedding-model drift silently invalidates a semantic cache**: swapping the embedding model (even a minor version bump) can make old and new embeddings' cosine similarity collapse toward random, so the cache starts confidently serving wrong answers with no visible error — treat an embedding-model change as a cache-flush event, not a transparent upgrade.
- **Context-clearing vs. prompt-caching tension**: aggressive tool-result/thinking-block clearing to save context space can *increase* cost if it's triggered often enough to repeatedly blow away a cache prefix that would otherwise be read at 0.1x — tune `clear_at_least`/thresholds against actual cache-hit telemetry, don't set-and-forget.
- **Speculative decoding has no fixed payoff** — it's entirely a function of how well the draft model's outputs match the target model's distribution; a stale or mismatched draft model can erase the expected latency win.
- **Quantization/distillation/pruning all trade a measurable accuracy delta for compute savings** — fine for high-volume, low-stakes tasks (classification, extraction); risky to apply blindly to anything safety- or correctness-critical without an eval pass confirming the delta is acceptable for that specific task.
- **RAG under-performs long-context when the task needs global reasoning** (synthesis across the whole corpus, not lookup) — defaulting to RAG everywhere "because it's cheaper" can silently degrade answer quality on exactly the tasks where it matters most.

## Practical Application to This Vault's Systems

- **This session (vr-brain, voice-driven)**: interactive, so batch API doesn't apply — the real levers are prompt caching (system prompt/tool schemas are static and should cache automatically across turns) and avoiding redundant large tool-result reads (memory files, already-read notes) that inflate the cacheable-but-still-billed prefix. If this session's own context-management/compaction is user-configurable, tune it against actual cache-hit telemetry per the pitfall above rather than maximizing clearing aggressiveness.
- **The auto-memory system itself is a compute-saving pattern**: persisting facts across sessions (this note included) means future sessions don't re-derive/re-research the same context from scratch — the memory index (`MEMORY.md`) staying short and pointer-based (rather than inlining full content) keeps that prefix cheap to re-read every session, the same principle Anthropic's memory-tool + context-editing combo formalizes at the API layer.
- **Workflow/Agent fan-outs** (used for broad research or multi-agent review): route cheap, mechanical sub-steps (grep-and-report, classification, simple extraction) to a lower model tier or lower effort setting, and reserve the default/high tier for synthesis and judgment calls — the routing/cascading principle above applied directly to this tool's `model`/`effort` options.
- **ThornBot / any always-on bot service**: if it fields a lot of repetitive queries (FAQ-shaped, narrow-domain), semantic caching is the highest-leverage addition beyond prompt caching — but implement the pitfalls above (TTL, threshold tuning, false-positive sampling) from day one rather than retrofitting them after a silent bad-answer incident.
- **Any future self-hosted/local model work** (see [Local Embedding Models for Semantic Search](kb://06-reference-local-embedding-models-for-semantic-search)): quantization is the first lever, before considering distillation, pruning, or fine-tuning — it's the cheapest to apply post-hoc and doesn't require retraining. If actually adapting a model to vault-specific tasks, LoRA/QLoRA over full fine-tuning unless the goal is a fundamental behavior change.
- **Any future document-heavy feature** (e.g. searching the full `~/Documents/aads` reference tree for SkyDestroyer, or large log corpora for [SOC → vr-brain integration](kb://soc-vrbrain-integration.md)): default to RAG/retrieval over stuffing full documents into context given the corpus sizes involved — reserve long-context stuffing for cases that need true cross-document synthesis.
